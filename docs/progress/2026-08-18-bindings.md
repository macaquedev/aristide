# 2026-08-18 — anything can be bound to anything

Two asks that turned out to be one: play from the computer keyboard, and
be able to say "this message means octave up" about a MIDI message *or* a
computer key. The second only has an honest answer if the computer
keyboard is an input like any other, so that is what it became.

## The vocabulary

A binding is a **trigger** from a **device** doing an **action**, and
both halves are text:

    trigger   note:36 | cc:64 | program:5 | key:Equal
    action    octave-up | octave-down | transpose-up | transpose-down
              transpose:<n> | transpose-reset | stop:<name>
              coupler:<name> | tremulant | cancel | panic
              enclosure:<name>

Text, not an enum on the wire, for three reasons: it reads as English in
a hand-edited `midi.toml`, it survives an organ that names things
differently (the names resolve through the same fuzzy matcher manual
names use, and a binding that names nothing this organ has is kept and
reported rather than deleted), and it is the shape a rule has to be in
before a scripting layer can generate one. The user wants that layer
eventually; this is the vocabulary it will be written in.

`Console` learned nothing new here. `State::run` is the single place an
action becomes an effect, so a binding, a menu item and
`POST /api/action` cannot mean different things by "cancel".

## Where the shift lives

`octave-up` moves the **input**, not the manual. It follows the compass
decision: how wide a keyboard is, and where it currently sits, are facts
about the hardware in front of the player. Put it on the manual and
shifting the computer keyboard would drag the MIDI keyboard and the
on-screen keys with it.

A pitch action with no named manual shifts every keyboard on the device
the trigger came from — which is what a transposer built into a console
means by "up" — and naming a manual narrows it.

A shifted keyboard reaches shifted pipes, so its shift is part of the
compass union: octave-up on a keyboard that already spans the set makes
the top octave repitched rather than silent. That is the same rule as
yesterday's, applied to a keyboard that has moved.

## The computer keyboard

Now a device called `Computer keyboard`, assignable in the MIDI tab like
any other, with its own transpose and its own bindings. Key presses go
to the server as *keys* (`POST /api/key?code=KeyZ`), not as notes: what
a key does is the server's to decide, so a key bound to an action does
not also sound, and `keys.js` is left drawing what the server decided.
The two QWERTY rows live in `control::KEYBOARD_ROWS`; the console's copy
labels caps, this one decides pitch.

Unassigned, it falls back to the principal manual instead of going
silent. The silence rule exists so a strange MIDI keyboard cannot blast
a division nobody plugged in; the computer keyboard is the instrument of
last resort on a machine that may have no MIDI at all, and the fallback
is implied rather than written — it becomes a real config entry the
moment the player changes something about it.

`−` and `=` are no longer special-cased anywhere. They are bindings the
player can move, and the Play menu's octave items fire the same actions
a piston would.

## Verified

- `cargo test --workspace` green, including: a bound note works the
  console and does not play; octave-up shifts the keyboard that pressed
  it (and the shift is saved); computer keys play, can be shifted, and a
  bound key plays nothing; the binding API's bind/learn/unbind round
  trip; `/api/action` and `/api/keyboard` move the computer keyboard.
- The snapshot is hand-written JSON, so a test now parses it and checks
  every field a console reads is where it claims to be — that caught
  `controls` landing inside `midi`.
- Preferences → Controls and the keyboard legend were rendered
  headlessly against a snapshot the server itself produced.
- Audible check is the user's, on their desktop rig.
